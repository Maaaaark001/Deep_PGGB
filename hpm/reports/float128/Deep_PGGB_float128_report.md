# Deep_PGGB 的 IEEE binary128（float128）版本

**实现、测量与代价** · 2026-11-25 · 评审稿（论文未改动）

> 问题：给 Deep_PGGB 单独做一个 float128 版本，128 位到底带来多少**有效**提升？要付多少**时间**？

---

## 0 结论

1. **精度上有效，而且很大。** 44.1→88.2、16 s、1 kHz、默认参数（C5 渐变、20 ms、800 ms 上下文）下，零差从 double 的 **307.2 dB** 提到 **440.2 dB**（+133 dB，ENOB 51.7 → 74.7 bit）；SINAD 从 307.1 dB 提到 **446.0 dB**。此时限制读数的已经不是算术，而是 20 ms C5 块渐变窗的谱尾。
2. **对音频交付没有意义。** 24-bit PCM 的理论下限约 146 dB，float32 约 150 dB；double 已经比 24-bit 高 161 dB，binary128 再高 294 dB。多出来的 130 dB 只对测量、验证和算法研究有用。
3. **代价是 82×。** 60 s 立体声 44.1→88.2：double 201× 实时 → binary128 **2.43×** 实时；16 s 单声道 152.8× → 1.51×（101×）。峰值内存 2.27×，文件 2×，并且必须自带四精度 FFT——FFTW 最高只到 x87 80 位。
4. **论文现有的五项失真指标看不到这个提升。** quad 输出与 double 输出只差 −303.7 dB rms，正好是论文口径的地板。要让论文口径"看见"128 位，分析链本身也得换成四精度；本文的 null / SINAD 链就是为此重写的尺子（自身地板 686 dB）。
5. **Windows 上的 `long double` 不是 binary128。** 它是 x87 80-bit，64 位尾数，sizeof 16 但有 6 字节填充。实测 80 位路径零差 372.9 dB，被 80 位的表示极限（394.6 dB）压住；想再往上只有 `__float128` + libquadmath（113 位尾数）。

## 1 三个精度档位

| 档位 | C++ 类型 | 尾数位 | 每样本字节 | 理论表示地板 | 本机实测零差（16 s，1 kHz） | 60 s 立体声吞吐 | 相对 double 耗时 |
|---|---|---:|---:|---:|---:|---:|---:|
| double | `double` | 53 | 8 | ≈ 320 dB | 307.16 dB | 201× | 1× |
| x87 80-bit | `long double` | 64 | 16（用 10） | 394.6 dB | 372.90 dB | 69×（16 s 单声道口径） | 2.2× |
| IEEE binary128 | `__float128` | 113 | 16 | ≈ 680 dB | **440.21 dB** | **2.43×** | **82×** |

"理论表示地板"指把 0.5 满量程正弦舍入到该类型后的零差极限（表中 394.6 dB 由实测 ruler 给出，320 dB 与 680 dB 由 2⁻⁵³ / 2⁻¹¹³ 折算）。三档实测值都低于各自的理论值：double 低 13 dB，80 位低 22 dB，128 位低 240 dB——最后这一档说明 **binary128 的算术能力还剩 240 dB 没用上，瓶颈已经换成了窗**。

## 2 实现

### 2.1 为什么必须自己写 FFT

FFTW 只有 `fftw_plan_dft_r2c_1d`（double）与 `fftwl_*`（long double）。在 MinGW/Windows 上 `long double` 是 x87 80 位，**没有** 113 位的变换可用。于是新增 `deeppggb/src/quad_fft.h`：一个 `__float128` 的混合基复数 FFT。

- 每个 plan 建一张主 twiddle 表 `exp(-2πik/N)`（sinq/cosq 计算，误差 ≤ 1 ulp），各级旋转因子取表中的精确下标，不做递推，避免误差随级数累积。
- 递归 DIT，radix 2 特化，radix 3 特化为 2 次乘法，其余 radix（5、7…）走直接 DFT。
- 两个 ping-pong 缓冲 + 一个输入缓冲，`thread_local`，plan 只读，因此一个 plan 可以被所有块线程同时使用。
- 实序列走 `fft_r2c`/`fft_c2r`；逆变换用 Hermitian 重建 `conj(FFT(conj(X)))`，所以 **c2r 的代价是 r2c 的两倍**（实测 5.02 s 对 2.40 s），这是后面可优化的一项。
- 精度自检：与朴素 DFT 比最大误差约 1e−33（−660 dB）；r2c→c2r 往返零差 666.2 dB。

### 2.2 接入引擎

`dpggb_core.cpp` 里所有改动都在 `#ifdef DPGGB_QUAD` 内，普通 DLL 构建（`build.sh`）不定义这个宏，因此 **默认产物的依赖与行为完全不变**：

- `Fftw<__float128>` 特化 + `QuadPlan`；`Wisdom<__float128>` 直接返回 0（没有 wisdom 可存）。
- 渐变窗权重、滚降权重、归一化 `1/(R·P)` 全部在四精度下计算（`cosq`/`powq`）。
- 新增 `resample_channel_q()`，输入输出都是 `__float128`；`precision=2` 的 double 便捷路径只用于兼容。
- 内存 64 字节对齐（`_aligned_malloc`）。

### 2.3 前端与构建

- `dpggb128.exe`（`src/dpggb_q_cli.cpp`）：读写原始 f128（16 B/样本，本机小端，交错），`--in f64/--out f64` 可与普通 float64 文件互转；其余选项与主 CLI 同名同义。
- `build_quad.sh`：`-O3 -std=c++20 -DDPGGB_QUAD -fext-numeric-literals`，链接 `-lquadmath`（静态 libgcc/libstdc++）。
- 工具链：g++ 16.2.0（MSYS2 UCRT64），`__SIZEOF_FLOAT128__ = 16`。

**互操作提醒**：numpy 没有 binary128，Windows 上 `np.longdouble` 是 80 位；`__float128` 的符号名是 `TF` 而不是 `g`，ctypes 绑定不可靠。因此 f128 文件目前只能在 C++ 工具链内闭环，这不是偷懒，是格式本身没有生态。

## 3 测量链：先证明尺子比被测对象准

这一节是整份报告的关键。**128 位的引擎会跑出 440 dB 的读数，而所有现成的音频分析代码（numpy float64 FFT）在 300 dB 左右就到顶了**——不先修尺子，读到的只会是尺子的地板。

### 3.1 尺子的地板（`dp_quad_probe ruler`，1 s、1 kHz、88.2 kHz、四精度分析）

| 尺子用法 | 零差 |
|---|---:|
| 四精度理想音 → 四精度分析 | 686.39 dB |
| 四精度理想音舍入到 double → 四精度分析 | 328.09 dB |
| 四精度理想音舍入到 80 位 → 四精度分析 | 394.57 dB |
| 四精度 r2c→c2r 往返再分析 | 666.19 dB |

结论：**尺子自己 686 dB，比任何被测档位至少高 200 dB**，所以下面 300–440 dB 的读数都是被测对象，不是测量系统。反过来看第二、三行：只要输出落在 double 上，读数就永远 ≤ 328 dB；落在 80 位上就永远 ≤ 395 dB。**这就是为什么"128 位有没有用"必须同时换 I/O 格式，否则测不出来。**

### 3.2 一个必须记住的坑：整数周期

零差分析用的是矩形窗投影 `g = <a,b>/<b,b>`，只有在**分析段包含整数个周期**时才是精确的。fs/gcd(f,fs) 是周期长度：1 kHz 在 88.2 kHz 下是 88.2 个样本的 1000 个周期（1 s 整），而 997 Hz 的周期是 88200 个样本（1 s），取 3.6 s 段就不是整数周期。

第一版没做这个对齐，997/1499/2003/2503/7001 Hz 全部读到 **262–298 dB**，而且 double 和 quad 读到同一个值——看着像"引擎在低频更差"，实际是矩形窗的泄漏裙边。把跳过段和长度都对齐到整周期之后，同一条尺子自检读到 689.8 dB，引擎读数才恢复真实。**凡是低于 −250 dB 的测量，先证明尺子，再信数字。**

### 3.3 分析口径

- 激励：16 s 整数 Hz 正弦，0.5 满量程，整数相位 `(f·n) mod fs` 用 113 位整数算，不经过浮点。
- 零差：跳过首尾各 5%，剩余段对齐整周期后一次投影；再看残差二次投影（防止第一次拟合吸收不干净）。
- SINAD/SFDR/ENOB：1 s 窗、每 0.25 s 一个、铺满全段；报**平稳区（2–13 s）中位数**与**最差一秒**，与论文 §4.3 一致。ENOB = (SINAD_FS − 1.76)/6.02。
- 速度：60 s 立体声、44.1→88.2、块 16 s、auto worker；三个精度**交错**跑 5 轮取中位数（机器满载会掉频，逐台跑完会把最后测的那个读成降频后的机器）。

口径差异（与论文对比时要注意）：论文的零差是"5 个 1 s 窗取中位数"，本文是"一个 14 s 整周期段"，同一台 double 引擎在这里读 307.2、论文读 303.5，差 3.7 dB 是估计量不同，不是引擎变了。SINAD 一边则对得上：本文 double 307.13 / 322.13 / 51.73，论文 305.8 / 320.2 / 51.51，差 ≤ 1.5 dB，说明**这条新尺子在 double 段与论文口径一致**，可以放心外推到 128 位。

## 4 结果

### 4.1 零差随频率（16 s，44.1→88.2，默认参数）

| 频率 | double | 80-bit（f80 I/O） | binary128 | 128 位增益 |
|---|---:|---:|---:|---:|
| 997 Hz | 307.35 | — | 438.77 | +131.4 |
| 1000 Hz | 307.16 | 372.90 | **440.21** | +133.1 |
| 5000 Hz | 306.71 | 372.21 | 411.66 | +105.0 |
| 15000 Hz | 306.24 | — | 345.35 | +39.1 |
| 17999 Hz | 305.47 | — | 310.04 | +4.6 |

别的倍率（1 kHz）：

| 倍率 | double | binary128 | 增益 |
|---|---:|---:|---:|
| 44.1→88.2 | 307.16 | 440.21 | +133.1 |
| 44.1→48 | 308.45 | 460.74 | +152.3 |
| 96→44.1 | 309.65 | 531.64 | +222.0 |

两条规律：

- **中频段 +130 dB 左右，接近源奈奎斯特迅速塌回地板。** 17999 Hz 只涨 4.6 dB，而且 **80 位和 128 位读同一个 310 dB**——这不是算术问题，是窗的问题（见 4.3）。
- **降采样比升采样高一大截**（96→44.1 的 531.6 dB）：降采样时砖墙把阻带能量切掉，而误差主要来自通带/过渡带附近的窗尾，被切掉后残差自然更低。

### 4.2 SINAD / SFDR / ENOB（16 s，1 kHz）

| 精度 | 平稳 SINAD | 中位 | 最差一秒 | SFDR | ENOB | 最差 ENOB |
|---|---:|---:|---:|---:|---:|---:|
| double | 307.13 | 307.14 | 306.86 | 322.13 | 51.73 | 51.72 |
| 80-bit（f64 I/O） | 328.09 | 328.09 | 328.09 | 340.46 | 55.21 | 55.21 |
| binary128 | **446.01** | 445.36 | **432.24** | 445.38 | **74.69** | 72.51 |

频率依赖（binary128）：5 kHz 平稳 419.77 / 最差 402.27 / ENOB 70.35；15 kHz 平稳 349.28 / 最差 339.78 / ENOB 58.59。

**最差杂散的位置很说明问题**：128 位下每一窗的最差谱线都恰好落在 **22050 Hz（源奈奎斯特）**，而不是某个算术杂散。20 ms 的块渐变窗是一个乘法器，它的谱尾落在源奈奎斯特上；砖墙在 22050 Hz 处把这条尾巴切了一刀，切口本身就是残差。double 段看不到它，因为 double 的算术误差更大、先把读数压住了。

> ENOB 74.7 bit 不要读成"74 位有效"，它只是残差能量折成的等效位数；超过 53 bit 就已经说明 pipeline 里没有 double 了。

### 4.3 地板由窗决定，不由算术决定

17999 Hz 的诊断（16 s、44.1→88.2，只改一个参数）：

| 条件 | 零差 |
|---|---:|
| C5 / 20 ms（默认），binary128 | 310.04 |
| C6 / 20 ms，binary128 | **352.64** |
| C5 / 80 ms，binary128 | 315.29 |
| C5 / 20 ms，double | 306.08 |

把窗从 C5 换到 C6（只改形状，不改长度）就 +42.6 dB；把长度从 20 ms 加到 80 ms 只 +5.3 dB。**形状比长度值钱**，与论文 §4.2 在 300 dB 段的结论一致，在 440 dB 段依然成立。上下文长度则是无关变量：C6/40 ms 下 400/800/1600/3200 ms 分别读到 475.11/474.30/474.09/474.08 dB（这段是早前 16 s 口径的补充测量）。

所以 128 位的正确读法是：**它把算术误差从读数里拿掉了，于是读数变成了"窗的谱尾 + 文件边界"的度量。** 440 dB 不是引擎的极限，是 C5/20 ms 这个设计的极限。

## 5 代价

### 5.1 吞吐（60 s 立体声，44.1→88.2，块 16 s，auto worker，5 轮交错）

| 精度 | 5 轮读数（×实时） | 中位 | 单次耗时 | 相对 double |
|---|---|---:|---:|---:|
| double | 209.82 / 201.19 / 202.45 / 199.68 / 194.26 | **201.19×** | 0.298 s | 1× |
| 80-bit（f64 I/O） | 88.07 / 90.26 / 88.77 / 86.68 / 81.96 | **88.07×** | 0.682 s | 2.28× |
| binary128 | 2.44 / 2.43 / 2.43 / 2.39 / 2.40 | **2.43×** | 24.7 s | **82.4×** |

16 s 单声道（单块，退化为单线程）：double 152.75×、80-bit（f80 I/O）69.37×、binary128 1.51× → 101×。

块长扫描（binary128，60 s 立体声）：块 4 s **2.75×**、块 8 s **3.19×**、块 16 s **2.43×**。四精度 FFT 对 cache 更敏感，块 8 s 比默认的 16 s 快 31%；但论文选 16 s 是为了接缝（SMPTE 边带），这个取舍在 128 位下没有变，所以默认仍是 16 s。

### 5.2 内禀 FFT 成本（网格 708588 / 1417176，即 16 s、44.1→88.2 的块）

| 项目 | 四精度 | FFTW double | 倍数 |
|---|---:|---:|---:|
| 建 plan（两个尺寸） | 3.600 s | ≈ 0.03 s | 120× |
| r2c | 2.399 s | 0.0071 s | 338× |
| c2r | 5.016 s | 0.0160 s | 314× |
| 每块合计 | 7.415 s | 0.0231 s | **321×** |

端到端只有 82× 而不是 321×，因为在同一台机器上 double 的 60 s 立体声只有 0.30 s（固定开销占比高），而四精度的 24.7 s 几乎全是 FFT。**engine 时间 > 99% 在四精度 FFT 里。**

### 5.3 时间构成与固定成本

- 16 s 单声道一次转换 10.6 s ≈ 建 plan 3.6 s（34%）+ 一块 r2c+c2r 7.4 s。
- 60 s 立体声 24.7 s 里 plan 只占 15%，其余是 8 个块（4 块 × 2 声道）的 FFT。
- **短文件被固定成本支配**：1 s 单声道 1.02 s（0.98× 实时），4 s 2.51 s（1.59×）。四精度路径在 1 s 文件上已经不是"快"或"慢"，而是"约等于实时"。

### 5.4 内存与文件

| 项目 | double | binary128 |
|---|---:|---:|
| 60 s 立体声峰值工作集 | 643 MB | 1459 MB（2.27×） |
| 每样本 | 8 B | 16 B |

### 5.5 时间换精度的边际收益

| 步进 | 多花的时间 | 买到的零差 | 每翻倍时间的收益 |
|---|---:|---:|---:|
| double → 80-bit | 2.2× | +65.7 dB | 58 dB |
| 80-bit → binary128 | 37× | +67.3 dB | 13.9 dB |
| double → binary128 | 82× | +133.1 dB | 20.9 dB |

第一步便宜，是因为它顺手把**输入表示**从 53 位提到 64 位；第二步贵，因为 80 位已经足够表达 440 dB 以内的信号，120 位买到的只是"算术不再参与"，而那部分本来就已经被窗压住了。换句话说：**如果目标只是 380 dB，80 位就够，代价 2.2×；要 440 dB，才需要 82×。**

## 6 论文口径下的意义

论文表 3 那五项（杂散、镜像、混叠、CCIF、SMPTE）在这台引擎上读到 −304、−319、−352、−332、−335 dBc。128 位版本跑同样的激励，**论文口径读到的仍然是这些数**，因为：

- quad 输出与 double 输出的 rms 差 = **−303.67 dB**（最大绝对差 9.6e−16），正好等于论文整套 float64 分析链的地板；
- 任何用 float64 FFT 做的指标，其噪声底就是 300 dB 量级，比被测对象的差还大。

结论不是"128 位没有提升"，而是"**128 位把引擎推到了论文测量能力的下面**"。要让论文展示这一层，只有两条路：把五项指标的分析也改为四精度（工作量大，且每一项都要重新验证尺子），或者只保留本文这条已经验证过的 null/SINAD 链，在论文里作为"精度上限"一节出现。

对音频工程的实际结论：**没有一台 DAC、没有一个交付格式、没有一段录音的噪声底在 −300 dB 附近**。128 位在这里的价值是"把算法定义本身测到底"，不是"更好听"。

## 7 什么时候值得用

**值得：**

- 需要 −300 dB 以下的参考信号（做测量系统的标定、做引擎的绝对误差归因）。
- 研究窗/渐变/砖墙的形状，而希望"算术误差"这个变量从实验里消失。
- 验证 double 路径的误差到底来自算术还是算法：本次对比直接证明 double 的 307 dB 里绝大部分是输入/输出的 53 位表示，而不是算法。

**不值得：**

- 任何交付、监听、归档路径（82× 换 130 dB，这 130 dB 在 24-bit 之下）。
- 实时或流式（2.43× 实时已经是离线口径；流式会再掉到 1× 以下）。
- 想"顺手提速"的场合：四精度 FFT 是软件模拟，比 FFTW 慢 300×，没有 SIMD 优化。

**建议的落地方式：**

- 保持 `-DDPGGB_QUAD` 为**可选构建**，默认产物不编、不链 quadmath，行为零变化（已如此）。
- 保留 `dpggb128.exe` 与 `dp_quad_probe.exe` 作为研究工具，不进入工具箱的引擎列表。
- 若后续要继续压时间：块 8 s（−24%）、实输入逆变换（c2r 减半，约 −25%）、四精度运算向量化（收益最大，工作量也最大）。

## 8 复现

```bash
cd deeppggb
bash build.sh          # 普通 DLL/exe，不含 quad 代码
bash build_quad.sh     # dpggb128.exe + dp_quad_probe.exe

# 尺子
./dp_quad_probe.exe ruler

# 零差：精度 0/1/2，16 s，1 kHz，块 16 s，C5，20 ms，上下文 800 ms
./dp_quad_probe.exe null 2 16 1000 16 0 20 5 800 44100 88200 0.05

# SINAD/SFDR/ENOB（注意：四精度分析本身要约 46 s，转换只要 10.8 s）
./dp_quad_probe.exe sinad 2 16 1000 16 0 20 5 800 44100 88200 0.05

# 速度（60 s 立体声，5 轮交错需手工重复三次精度）
./dp_quad_probe.exe speed 0 60 16 0
./dp_quad_probe.exe speed 2 60 16 0

# 文件前端：f64 进、f128 出、再读回来
./dpggb128.exe 44100 88200 in.f64 out.f128 --in f64 --out f128
./dpggb128.exe 88200 88200 out.f128 back.f64 --in f128 --out f64
```

f128 文件格式：原生小端、16 字节/样本、交错。上面最后一次往返已验证**逐位相同**（`back.f64` 与 `out.f64` 完全一致）。

## 10 局限

1. 只覆盖 16 s / 60 s、44.1↔88.2、44.1→48、96→44.1；其他倍率与块长未逐一测。
2. 论文五项失真指标没有在四精度下重测——这正是第 6 节的论点，但如果要写进论文，需要为每一项重做四精度分析并重新验证尺子。
3. 80 位只测了 16 s 单声道，没有 60 s 立体声口径。
4. 速度是单机、单会话读数；跨会话 ±20%，只能同会话交错比较。
5. 四精度 FFT 是"能跑、跑得对"，不是"跑得快"：没有 SIMD、没有实数打包、没有 wisdom，plan 每次进程重建 3.6 s。
6. 文件互操作是断的：numpy/ctypes 都不方便处理 binary128，f128 文件只在 C++ 工具链内闭环。

## 11 一句话总结

**128 位不是"更快"，也不是"更好听"，它是把 Deep_PGGB 的误差从"算术"这一层剥掉、露出下面的"窗"这一层；为此付 82× 的时间。对论文而言，它证明了一件事：当前 300 dB 的读数全部是 double 的表示极限，算法本身还有至少 130 dB 的余量。**
